### [P2] `previewNumber` ignores the period reset (PR 6)
- Category: defect (design gap)
- Rule: spec line 533 ("Period tokens use the workspace timezone"; sequence reset by period); plan Task 18 lines 256-257 (`previewNumber` "uses the same `formatNumber` with `counter + 1`")
- Evidence: `allocateNumber` resets the counter when `periodKey` differs from `last_reset_period`; the preview as written does not.
- Failure scenario: on 1 January (workspace timezone) before the first issue of the year, the preview shows `INV-ACME-2027-0057` while the allocator issues `INV-ACME-2027-0001`. The done-when "Pattern preview matches issued numbers" fails exactly at period boundaries.
- Required correction: the preview must compute the effective counter with the same reset function the allocator uses (one shared function), and `preview-matches-issued.test.ts` must include times just before and after a period boundary and a timezone whose date differs from UTC.
- Owner: builder
- Verification: the shared function is named in Task 18; the test cases exist.
- Disposition (P2 only): deferred to Phase 2 PR 6 (stop-and-ask before the PR; Bob checks it first, plan line 246)
- Status: open

### [P2] Free text in a numbering pattern has no character or length bound (PR 6)
- Category: material risk (input validation)
- Rule: UNI-03 (validate at boundaries); spec line 533 says only "+ free text"
- Evidence: plan Task 17 line 250: `parsePattern` "accepts only the tokens plus free text". A number ends up in PDF file names, `Content-Disposition`, email subjects and URLs from Phase 4 on.
- Failure scenario: an Admin saves a pattern containing `/`, `..`, quotes, CR/LF or very long text; later it reaches a file name or a header.
- Required correction: bound the free text (a builder proposal such as letters, digits, space and `-_/.#`, with a maximum total length) in `limits.ts`; Charlie confirms the set at the PR 6 stop-and-ask because the spec leaves it open. Add tests for each refused character class.
- Owner: builder (Charlie confirms)
- Verification: `limits.ts` constant and Zod/parse tests; DECISIONS line.
- Disposition (P2 only): deferred to Phase 2 PR 6 stop-and-ask
- Status: open

### [P2] Template values substituted into an email subject are HTML-escaped but not stripped of line breaks (PR 8)
- Category: material risk (header injection)
- Rule: FILE-05/06; plan Task 24 line 302 (values HTML-escaped, single pass)
- Evidence: HTML escaping suits the body. A subject is a header: it needs CR/LF removed (and should not show `&amp;`). The plan treats subject and body the same.
- Failure scenario: a customer name or other field value containing a line break is substituted into the subject and the SMTP/API layer receives an extra header line, or the subject shows escaped entities.
- Required correction: `render` takes the output context (subject = plain text with CR/LF and control characters removed; body = HTML-escaped); tests for both.
- Owner: builder
- Verification: `render.test.ts` cases for subject and body.
- Disposition (P2 only): deferred to Phase 2 PR 8
- Status: open
