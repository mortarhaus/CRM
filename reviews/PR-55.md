### Findings

**[P2] The outdated-browser notice is shown in browsers where nothing is degraded.** Disposition: before merge.
- **Where:** `apps/web/src/components/outdated-browser-notice.tsx`, `lacksRequiredFeatures()`. It returns true when `!("command" in HTMLButtonElement.prototype)`.
- **Why it's wrong:** the script only runs when JavaScript is on. With JavaScript on, the phone menu drawer already falls back to `showModal()`/`close()` when invoker commands are missing (`components/shell/menu-drawer.tsx` lines 52-62). The one case invoker commands are needed for is JavaScript off, where this check can't run. So the check never detects real degradation, and it raises a false one.
- **Who sees it:** every browser with JavaScript but without invoker commands: Safari before 26.2 (including iPhones that can't go past iOS 18), Firefox before 144 (including the ESR line), and Chrome or Edge before 135. They get "parts of CRM may not work properly" on every page, including the sign-in page, and later the client-facing pages. Nothing on those pages is broken.
- **Charlie's direction (PR #53 R2):** show the notice only "if it is not supported". This breaks it.
- **Fix:**
  - Drop the invoker-commands test from `lacksRequiredFeatures()` and keep the `<dialog>` test.
  - In `e2e/shell.spec.ts`, turn the "lacks invoker commands" case into the opposite: the notice is absent, and the drawer still opens, closes on Esc and returns focus with the property deleted.
  - Update the component comment and the DECISIONS entry. The no-JavaScript plus no-invoker-commands case stays the accepted residual from PR #53 R2.

### [P3] Notes (optional)
1. **The brand token loses its fill in browsers without native `light-dark()`.**
   - **Why:** the production CSS build compiles `light-dark()` into lightningcss variables for Next's default targets, which include Safari 16.4. I confirmed this with the repo's own lightningcss. But the runtime `<style nonce>` from `lib/brand.ts` emits raw `light-dark()`.
   - **Effect:** in Safari 16.4–17.4 (and similar), a workspace with a custom colour gets an invalid `--accent`, so filled buttons lose their background while keeping white text. The default accent is unaffected, because it is a plain hex.
   - **Why only P3:** those browsers do get the notice (the `@supports not (color: light-dark(...))` rule), so this is within Charlie's "degraded, with a notice" ruling.
   - **Optional fix:** emit `:root{--accent:L;--accent-foreground:LF}` first, then the `light-dark()` rule inside `@supports (color: light-dark(#000,#fff))`.
2. **Hint text for the hue slider.** The picker's key hint only describes the saturation and brightness area. Add "Hue: left and right" or similar.
3. **The previous state is validated when an action has no `fromForm`.** If an action without `fromForm` is wired into `useActionState` later, it validates the previous state, not the form. The new test documents this. A lint rule or a type-level guard would catch the mistake, but this is optional.
4. **Size:** about 1,280 lines against the 400 target. The builder offered a split (2b-i branding, 2b-ii notice). I reviewed it whole; the files overlap. No action.
