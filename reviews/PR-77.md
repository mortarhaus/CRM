### Findings

### [P1] Keep raw action payload reads behind the authentication and role checks

- Category: guardrail mismatch.
- Rule: AUTH-01 and the action order in Core Sales spec “Validation” (`docs/superpowers/specs/2026-09-27-core-sales-design.md:432`). The updated contract in `action.ts:166`–`:171` permits reading only the rendered-workspace marker before step 4.
- Evidence: `apps/web/src/lib/auth/action.ts:200` calls `takeRendered` before `requireWorkspaceMember` calls `getCurrentSession`. For an object input, `:136` uses object rest and reads the other enumerable properties before both checks. A sandboxed probe of the real wrapper with a benign accessor observed the payload read before the session call. It ran even when the action ultimately returned `UNAUTHENTICATED`, `WORKSPACE_CHANGED` or `FORBIDDEN`. The ordinary stale FormData case still skipped the business-payload parser and the write transaction.
- Failure scenario: A raw object carries an app-supplied computed field. Preparing the input evaluates that field even for a caller the guard will refuse. This regresses the wrapper's prior ordering without changing which workspace it uses for writes.
- Why it matters: This is the shared authorization boundary. The present raw production call binds a plain object, so I did not verify a production exposure. The wrapper should preserve the documented order for arbitrary raw inputs and future callers.
- Required correction: Read the session first. During tenant resolution, extract and compare only the workspace marker. Strip that marker and prepare the other fields after the role check, immediately before Zod.
- Owner: builder.
- Verification: Add order assertions for the workspace marker and unrelated payload fields. Verify that missing-session, stale-workspace and wrong-role refusals leave the business payload unread, and that matching authorized actions still parse and write under the session workspace.
- Status: open.
