### [P2] The "New" menu opens partly off-screen at 320 px
- Category: defect (accessibility, WCAG 2.2 SC 1.4.10 Reflow)
- Rule: FE-70; plan Task 2 "Mobile-320"; PR 1 done-when ("the shell renders … at all three widths")
- Evidence: `components/shell/new-menu.tsx:20` puts the panel at `absolute right-0 … min-w-44`. At narrow widths the top bar's action group wraps onto its own line, so `<details>` is the first item at the left edge, and the 176 px panel, aligned to the right edge of a ~109 px button, extends past the viewport's left edge. I measured it in Chromium with the PR's compiled CSS (`.next/static/chunks/32d06-21csr1l.css` from my `pnpm build`) and the top bar's markup, panel open:

  | width | `<details>` x | panel x | "Workspace" link x |
  |---|---|---|---|
  | 320 | 16 → 125 | **−51** → 125 | **−46** → 120 |
  | 768 | 128 → 237 | 61 → 237 (over the sidebar) | 66 → 232 |
  | 1280 | 616 → 725 | 549 → 725 | 554 → 720 |

  `document.documentElement.scrollWidth` stays 320, so `expectNoHorizontalOverflow` cannot catch it, and no test opens the menu at 320.
- Failure scenario: at 320 px a user opens "New" and the only item's start is cut off ("…kspace"), with no way to scroll to it.
- Required correction: anchor the panel so it stays inside the viewport (for example `left-0` when the group wraps, or `left-0 sm:left-auto sm:right-0`), and add an e2e at mobile-320 that opens the menu and checks that the link's bounding box is inside the viewport, plus an axe scan in the open state.
- Owner: builder
- Verification: the new test passes at chromium, tablet-768 and mobile-320.

### [P2] The theme route handler is a new mutating entry point outside `action()`, but DECISIONS records "Exception to a rule? no" and no AUTH-01 ruling
- Category: spec/guardrail mismatch (hard rule)
- Rule: AUTH-01 (hard): "Every mutating server entry point goes through `ACTION_WRAPPER`"; `PROJECT.md` "Hard-rule rulings" (AUTH-01 deviations are recorded as a Bob ruling plus Charlie's confirmation, with the conditions under which they conform)
- Evidence: `(app)/theme/route.ts` exports `POST`, sets a cookie and does not go through `action()`. DECISIONS 2026-11-04 "Phase 2 PR 1" item (3) explains why, then says **Exception to a rule? no**. `entry-points.test.ts` classifies the file, which satisfies the test but is not a ruling.
- My ruling (proposed): **a conforming interpretation, not an exception**, because the handler changes no server-side state: it writes no database row, reads no tenant data, and only sets the caller's own display-preference cookie. It conforms only while all of these hold: (a) no database read or write beyond the session lookup; (b) same-origin `Origin` required (403 otherwise); (c) signed-in session required; (d) the value allow-listed (`parseTheme`); (e) the redirect target limited to a same-origin path (`returnPath`); (f) classified in `entry-points.test.ts` with these conditions. I checked all six at this head. Any future cookie- or preference-only route needs the same conditions, and anything that touches the database goes through `action()`.
- Failure scenario: without a recorded ruling, "route handler plus classification row" becomes the precedent for skipping `action()` on the next endpoint that does write data.
- Required correction: in the DECISIONS entry, change **Exception to a rule?** to "no: AUTH-01 conforming interpretation (Bob, PR #53 R1), conditions (a)-(f), pending Charlie's confirmation", and repeat conditions (a)-(f) in the `coveredBy` text in `entry-points.test.ts` (the "no database" condition is the one missing). After Charlie confirms, `setup` adds the ruling to `PROJECT.md` "Hard-rule rulings".
- Owner: builder (Charlie confirms)
- Verification: the DECISIONS text and the test row.
