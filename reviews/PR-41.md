### Findings

### [P2] The TEN-09 lint misses connection-level forms of the workspace setting
- Category: material risk (enforcement gap; the code today complies)
- Rule: TEN-09 (hard), UNI-04, PROJECT.md §9 "Workspace context"
- Evidence: I ran ESLint with the head config on `apps/web/src/lib/probe.ts`:
  - `postgres(url, { connection: { 'app.workspace_id': id } })`: **not reported**.
  - `postgres(url, { connection: { options: '-c app.workspace_id=' + id } })`: **not reported**.
  - `` sql`select "set_config"('app.workspace_id', ${id}, false)` `` (a quoted function name is valid SQL): **not reported**.
  - For comparison: `ALTER ROLE crm_app SET app.workspace_id`, `pg_catalog.set_config(` and `set app.workspace_id to 1` are all reported.
- Failure scenario: a later PR adds a second client (for example the worker's tenant connection) and passes the workspace as a postgres.js startup parameter. Every connection in that pool then carries a session-level workspace. A bare query on it sees that workspace's rows, and the `nullif` guard does not help. This is the pooled-connection leak that TEN-09 bans. `pnpm lint` stays green.
- Why it matters: TEN-09 is hard, and the lint is its only automatic guard until `action()` lands. Today no app code uses these forms: `git grep "app.workspace_id\|set_config"` outside tests and migrations finds only `db/workspace.ts:32` and the predicate constant in `test/catalog.ts`.
- Required correction:
  - Make the pattern accept an optional quote around the function name (`"?set_config"?\s*\(`).
  - Report a property key or string that names an `app.` setting as a connection parameter. For example: `Property[key.value=/^app\./]`, plus a literal or template matching `-c\s*app\.`.
  - Add the three probes above as fixtures in `lint-rules.test.ts`.
- Owner: builder
- Verification: the three new fixtures are reported, the existing "does not report" case stays clean, and `pnpm lint` exits 0.

### Residual risks and test gaps
- The builder's "nesting test deadlocks for 30 seconds without the guard" is expected. The pool has one connection and the outer transaction holds it. Without the guard, the inner `runInWorkspace` waits for a second connection that never comes. With the guard, it throws before it asks for a connection. No further investigation is needed.
- If a later Better Auth version runs organization create inside an adapter transaction, the hook's separate `runInWorkspace` transaction would wait on an uncommitted `organization` row for the FK check. This could hang. Recheck the hook on any Better Auth upgrade.
- From PR 4, a Better Auth create call made inside `withWorkspace()` (for example from an `action()`) would throw `NestedWorkspaceError` in the hook. The organization would exist without its row until the Task 14 heal runs. PR 4 should keep organization create outside `action()`'s workspace transaction, or test this path.
- A Phase 0 database upgraded without `down -v` has workspaces with no `workspace_settings` row. The PR 1 runbook already requires `down -v` for Phase 0 dev data, and the Task 14 heal covers the rest.
- A write test that moves a row from A to B (`UPDATE … SET workspace_id = B` inside A) is not in the harness. The catalog test forces WITH CHECK on every UPDATE policy, so the structure covers it. A direct test would make it explicit when Phase 2 adds tables with a non-key `workspace_id`.
