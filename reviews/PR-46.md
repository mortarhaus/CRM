### What I checked in the code (no defect found)
- **Atomic enqueue (EVT-01):** `enqueue.ts` sends through `fromDrizzle(tx, sql)` in the caller's `withWorkspace()` transaction. The job id is the event id, so a repeated send makes one job. `getSendBoss()` is called only in `enqueue.ts`; a test scans `src` for other call sites.
- **Payload rules:** `eventPayloadSchema` allows only a uuid, a canonical decimal string or a safe integer. A bigint is refused before any statement. Errors name the field only. `jobDataSchema` requires `workspaceId` and `<name>Id` keys with uuid values.
- **Tables and RLS:** `domain_event` has RESTRICTIVE `FOR ALL TO crm_app, crm_purge`, PERMISSIVE SELECT and INSERT for `crm_app`, and grants of SELECT and INSERT only (append-only). `notification` adds UPDATE of `read_at` only. Both use `FORCE ROW LEVEL SECURITY` and the `nullif(current_setting('app.workspace_id', true), '')::uuid` form. `crm_purge` holds no grant on either.
- **Handler:** `domain-event.ts` runs under `withWorkspace(workspaceId)` from the job. RLS hides another workspace's event, so a mismatched job fails and retries. The queue `domain_event` has `retryLimit` 5, backoff and a dead-letter queue (`0016_pgboss_queues_grants.sql:5-7`). `boss.work` uses the default batch size of one (`worker/start.ts:31`), so one failed job cannot re-run a committed one.
- **Health:** `queue` compares `pgboss.version` with `PGBOSS_SCHEMA_VERSION = 43`. I read `pg-boss@12.35.0/dist/schema.json`: version 43. The body shows `ok` or `error` only, never error text.
- **PgBouncer helper:** the image is pinned by tag and index digest. No new npm dependency. Test passwords come from the test helper.
- **Note for later:** `notification.target_type`/`target_id` is a polymorphic reference with no same-workspace trigger. The spec's trigger list (`share_link`, `line_item`, `document_artifact`, `signature`, `version_retention`) does not name `notification`, and the table has no producer until Phase 7. The Phase 7 plan should decide whether it needs one.
