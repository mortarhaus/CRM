### [P1] Organization invitations remain valid for 48 hours instead of 30 minutes
- Category: spec/guardrail mismatch
- Rule: AUTH-08; approved spec “Authentication and sessions”
- Evidence: `apps/web/src/lib/auth/config.ts:36` enables `organization()` without `invitationExpiresIn`. The installed Better Auth 1.7.6 `organization/adapter.mjs` uses `options?.invitationExpiresIn || 3600 * 48` when creating an invitation, and `routes/crud-invites.mjs` uses the same default on resend. The spec at `docs/superpowers/specs/2026-09-27-core-sales-design.md:702` requires reset and invitation links to expire after 30 minutes. The route is exposed by `apps/web/src/app/api/auth/[...all]/route.ts:4-10`; the plugin can create and return an invitation even without `sendInvitationEmail`.
- Failure scenario: an invitation ID issued by the active organization endpoint can be accepted hours after the required 30-minute window.
- Why it matters: the longer credential lifetime violates an approved security bound.
- Required correction: set the plugin invitation expiry to 30 minutes, including resend, and pin create/accept-after-expiry behavior in a real-Postgres auth test. When password reset is enabled later, set its separate default to the spec's 30 minutes too.
- Owner: builder
- Verification: inspect config and prove a created invitation expires at about 30 minutes and is rejected after expiry; inspect resend's expiry as well.
- Status: open

### [P1] Production HTTP origin can issue a session cookie without `Secure`
- Category: guardrail mismatch / material risk
- Rule: UNI-18
- Evidence: `apps/web/src/lib/env.ts:9` accepts any URL as `APP_URL`; `.env.example:7` illustrates HTTP; `apps/web/src/lib/auth/server.ts:10` passes that URL to Better Auth. In installed Better Auth 1.7.6 `cookies/index.mjs`, an HTTP `baseURL` selects no secure-cookie prefix, and `createCookie()` sets `secure: !!secureCookiePrefix`. There is no production-origin check or explicit secure-cookie setting in `apps/web/src/lib/auth/config.ts:15-37`.
- Failure scenario: `NODE_ENV=production` with a non-loopback `APP_URL=http://...` passes validation and emits an auth cookie without `Secure`.
- Why it matters: a production session cookie can travel over cleartext HTTP, contrary to UNI-18.
- Required correction: reject non-HTTPS, non-loopback production `APP_URL` values and/or force secure auth cookies for production public origins. Keep local loopback development workable. Pin the cookie attributes and invalid-origin refusal in tests.
- Owner: builder
- Verification: production config with an HTTP public origin is refused or yields no usable insecure auth cookie; HTTPS yields `Secure`, `HttpOnly` and `SameSite`.
- Status: open
