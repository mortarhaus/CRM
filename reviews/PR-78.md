### Findings

### [P1] Preserve the JavaScript draft when a refusal follows a successful save

- Category: defect.
- Rule: the with-JavaScript behavior in `docs/DECISIONS.md:7`, FE-70 and the same-process retry principle in WCAG 2.2 SC 3.3.7.
- Evidence: `apps/web/src/app/(app)/catalog/service-form.tsx:137` includes the returned service ID in the input subtree key only while the latest result is successful. A later refusal drops the ID. The uncontrolled fields at lines 148–189 now initialize exclusively from the saved or initial values. The fallback for typed text was removed with the echo. The alert at line 198 omits the draft-loss note because `postedHere` was set by the JavaScript submit.
- Failure scenario: An Owner adds one service successfully. Without leaving the form, they type a second service and make a price validation error. The previous success key becomes the failure key, remounting the fields with their initial values. The same transition can restore the last saved values on edit. The price error is shown, but the user also has to reconstruct valid fields they just entered.
- Why it matters: This changes the JavaScript workflow the decision explicitly preserves. It can lose the full unsaved draft while providing only the normal validation alert.
- Required correction: Keep field identity stable across a refused submission. Trigger an intentional reset on a successful save or genuine workspace/service change. Keep the draft locally and keep arbitrary input out of the action response.
- Owner: builder.
- Verification: Add a JavaScript browser regression that saves successfully, stays on the form, then submits a new draft with a price error. Assert the name, description, unit, price, currency and taxable choice survive the refusal and the corrected retry saves. Cover successive edits as well if the form shares the same reset logic.
- Status: open.

An isolated render probe ran the checked-out form with fixture action states and stubbed React hooks. It observed the create key change `new-service-a` → `new-` and edit key change `2-service-a` → `2-`, both with initial/saved defaults and no draft-loss note. The probe inspected the emitted element tree. It did not drive the full browser sequence. The framework documentation describes the effect of a changed key and preservation of unaffected client state during a refresh. The WCAG guidance includes retries after a validation error as an example of redundant-entry avoidance. [React form keys](https://react.dev/learn/preserving-and-resetting-state#resetting-a-form-with-a-key) · [Next.js router refresh](https://nextjs.org/docs/app/api-reference/functions/use-router) · [W3C Redundant Entry guidance](https://www.w3.org/WAI/WCAG22/Understanding/redundant-entry.html).

### [P3] Remove the wrong direction from the no-JavaScript alert

- Category: defect.
- Rule: FE-22 and A11Y-03, accurate correction instructions.
- Evidence: `apps/web/src/lib/auth/messages.ts:299`–`:300` points to the form or fields below. `service-form.tsx:148`–`:194` renders the input group before the alert at line 196.
- Failure scenario: After a rejected no-JavaScript submission, a user follows the alert and looks after it for the fields that need re-entry.
- Why it matters: The fields are still labeled and associated with their errors, so the isolated issue is the recovery copy.
- Required correction: Describe the initial or saved values without pointing to a location, or place the alert before the fields.
- Owner: builder.
- Verification: Read the refusal copy in DOM order for both create and edit.
- Status: open (optional).
