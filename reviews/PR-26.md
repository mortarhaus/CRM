### [P2] Name fields still silently truncate valid Unicode input
- Category: defect / consistency
- Rule: UNI-02, UNI-03, FE-32
- Evidence: `apps/web/src/app/(auth)/sign-up/sign-up-form.tsx:24` retains `maxLength={NAME_MAX_LENGTH}` (100) and `apps/web/src/app/(app)/workspaces/create-workspace-form.tsx:24` retains `maxLength={WORKSPACE_NAME_MAX_LENGTH}` (80). `apps/web/src/components/ui/input.tsx:11` passes these to native `<input>`. The server counts Unicode code points in `apps/web/src/lib/auth/input-limits.ts:41-42`; HTML `maxlength` counts UTF-16 code units and may prevent entry beyond the limit ([HTML Standard §4.10.19.3](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html), [Infra string length](https://infra.spec.whatwg.org/)). The owner removed the password `maxLength` for precisely this mismatch (`docs/DECISIONS.md:13`).
- Failure scenario: A user pastes a name containing astral characters near the 100 or 80 code-point limit. The browser can cut the string before submit, and the server stores the shortened name without ever showing its limit message. For example, 80 emoji are valid under the workspace policy but occupy 160 UTF-16 units, so the field can stop at 40.
- Why it matters: The UI and server implement different limits, causing silent alteration of names. Impact is isolated to these two text fields, so this is P2 rather than the default P1 for a guardrail mismatch.
- Required correction: Remove the native `maxLength` from both fields or use a mechanism that counts code points without truncating. Keep the server's 100/80 checks and show a clear over-limit message. Cover a pasted astral-character boundary in the form verification, with and without JavaScript.
- Owner: builder
- Verification: A valid 80-code-point workspace name and 100-code-point user name containing astral characters arrive intact; one code point over each limit is refused visibly by the server.
- Disposition: before merge
- Status: open
