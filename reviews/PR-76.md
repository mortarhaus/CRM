### Findings

### [P0] A template opened in one workspace can overwrite a template in another

- Category: defect.
- Rule: spec “Authorization” and “Tenancy”, TEN-08, and the expected-version protection for template edits.
- Evidence: `apps/web/src/app/(app)/settings/templates/page.tsx:21` reads the template for the workspace active when the page renders. `template-form.tsx:190`–`:193` submits the event and version, with no original workspace context. `apps/web/src/lib/auth/action.ts:79`–`:85` resolves the active workspace again at submit, and `:203` opens the write transaction there. `apps/web/src/db/templates/email-templates.ts:62`–`:74` accepts a matching number, including 0 for any workspace without a row. An isolated probe of the real action and wrapper confirmed that a form prepared under fixture A reached the write callback under fixture B. The probe stubbed the session and DB boundary, with no physical write.
- Failure scenario: An Admin or Owner of two workspaces leaves a template editor open, switches the active workspace in another tab, and saves the original form. When the event versions match, the second workspace receives the first workspace's text. An existing template in that workspace can be overwritten. Other Admins and Owners in that workspace can then read the text.
- Why it matters: A normal workspace switch can pair one tenant's data with another tenant's write, leading to incorrect settings or disclosure of editable text.
- Required correction: Bind the form to the workspace it was rendered for and refuse a mismatch before writing. Keep the session as the authority for the destination. Reset the editor's local state on a workspace change.
- Owner: builder.
- Verification: Cover a stale form across two disposable workspaces with matching versions, including the unsaved-default version. Assert the refusal and that neither workspace gains a template or audit change. Exercise an ordinary save and restore in the intended workspace.
- Status: open.

### [P1] The invalid-input response echoes free-form text that can contain personal data

- Category: guardrail mismatch.
- Rule: the form echo contract in `apps/web/src/lib/auth/action.ts:40`–`:42` and `:168`–`:171`, with UNI-09 and the privacy reasoning from PR #75.
- Evidence: `apps/web/src/app/(app)/settings/templates/actions.ts:52`–`:53` declares subject and body safe for echo. `apps/web/src/lib/settings-input.ts:73`–`:83` copies both strings as posted. The isolated action probe confirmed that a rejected malformed body was returned verbatim, including a synthetic contact address. The action rejected a Staff fixture before validation or echo.
- Failure scenario: An authorized editor includes a direct contact address in a template and makes a placeholder typo. The entire submitted body is returned in the failure payload.
- Why it matters: The shared action contract restricts echo to fields safe to return verbatim. PR #75 specifically established that the same subject and body can hold personal data. The scoped audit remains metadata-only.
- Required correction: Keep arbitrary template text out of refusal echo. Preserve the draft in client state where available and retain a usable no-JavaScript refusal and retry path with field errors.
- Owner: builder.
- Verification: Submit a synthetic address in an invalid subject and body. Assert the action response carries field errors and omits the posted text. Verify the no-JavaScript form can correct and resubmit.
- Status: open.

### [P1] The self-check omits applicable accessibility rules and has no keyboard verification of the editor

- Category: guardrail mismatch.
- Rule: A11Y-01, A11Y-02, A11Y-03, A11Y-06, FE-70 and reviewer §3.
- Evidence: The PR body lists FE rules and then §9 rows, with no A11Y rule rows. Its FE-70 row treats native controls and axe as keyboard coverage and acknowledges no keyboard walk. `apps/web/e2e/email-templates.spec.ts:44`–`:91` uses clicks, fills and axe. It does not exercise keyboard navigation, activation and focus after save, refusal or restore. The stale case is in the action test and the e2e suite has no failed-submit check.
- Failure scenario: The effect that returns focus to Save after a response can regress while the existing axe and mouse-driven tests still pass.
- Why it matters: The frontend pack requires behavior verified in a real browser. Programmatic labels and clean axe results verify part of the requirement.
- Required correction: Add the applicable A11Y rows and supply browser evidence for keyboard navigation, submit or restore, and focus and error handling after refusal. Correct the FE-70 and TEN-08 rows to reflect the actual paths exercised.
- Owner: builder.
- Verification: Inspect the self-check and named browser results at the corrected head. At minimum, exercise keyboard operation and focus at desktop and mobile widths.
- Status: open.

### [P2] The settings intro implies edits change outgoing email

- Category: defect.
- Rule: Q23 Phase 2 scope, `docs/DECISIONS.md:10` and the matching email runbook.
- Evidence: `apps/web/src/lib/auth/messages.ts:297`–`:298` says that CRM uses default text “until you change a template”. `page.tsx:46` displays this for every event. `docs/runbooks/phase-1-security.md:227`–`:229` says the bank-details job still sends the Q18 default after an edit, and no Phase 2 sender reads saved rows.
- Failure scenario: An Owner changes the bank-details notification and expects the newly saved wording to go out on the next bank-details change. The Q18 default is sent.
- Why it matters: The mismatch is visible on the normal successful path and misstates the effect of changing a live notification.
- Required correction: Describe saving and previewing the workspace copy and make clear on the page that saved edits do not affect Phase 2 delivery.
- Owner: builder.
- Verification: Read the rendered copy for the owner-notification event after save and compare it with the current runbook and sender.
- Disposition: before merge.
- Status: open.
