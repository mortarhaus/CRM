### [P2] The shipped signed-URL contract is known not to satisfy FILE-04 on the selected production provider
- Category: guardrail mismatch
- Rule: FILE-04
- Evidence: `apps/web/src/adapters/storage/s3.ts:86-98` signs only `ResponseContentDisposition: attachment`; `docs/runbooks/phase-2-storage.md:74-76` records that S3 and R2 do not add `X-Content-Type-Options: nosniff`. FILE-04 at `agents/guardrails/files-templates.md:12-13` requires signed downloads to have expiry ≤10 minutes, attachment disposition, and `nosniff`. The PR self-check nevertheless marks FILE-04 pass. MinIO happens to add the header; the implementation does not guarantee it. AWS documents that the overridable GetObject response headers are limited and do not include `X-Content-Type-Options`: https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html
- Failure scenario: a future caller uses the public `signedGetUrl` adapter method exactly as exposed against R2 and serves attacker-controlled content without the required `nosniff` response header.
- Why it matters: this creates a reusable security API whose advertised guardrail is only true for the test emulator. Severity is reduced from the default P1 to P2 because there is no current caller and the current logo route independently sets `nosniff`, so the impact is isolated to future use.
- Required correction: before merge, either remove/defer `signedGetUrl` until the R2 delivery mechanism can guarantee FILE-04, or implement and contract-test a production delivery path (for example a controlled same-origin/edge response) that sets all three required properties. The self-check and runbook must describe the actual guarantee, not MinIO's incidental behavior.
- Owner: builder
- Verification: the adapter no longer exposes an unsafe direct-use path, or an R2-representative contract test proves TTL, attachment, and `nosniff`; FILE-04 evidence is updated.
- Disposition (P2 only): before merge
- Status: open

### [P2] Any S3 404 is treated as a missing object, hiding missing-bucket outages
- Category: defect
- Rule: UNI-05 / operational resilience
- Evidence: `apps/web/src/adapters/storage/s3.ts:14-18,60-83` defines `isMissing` as any `S3ServiceException` with HTTP 404 (or `NoSuchKey`), so both `get` and `head` return `null`. AWS documents that `NoSuchKey` and `NoSuchBucket` both map to HTTP 404 and recommends using the S3 error code rather than status alone: https://docs.aws.amazon.com/AmazonS3/latest/userguide/ErrorBestPractices.html. The runbook says a missing bucket should be diagnosed as an adapter error (`docs/runbooks/phase-2-storage.md:107-112`), which the code contradicts.
- Failure scenario: production is configured with a deleted or misspelled bucket. Logo reads return ordinary 404s and broken images instead of throwing/logging `StorageError`, so monitoring and operators misdiagnose a configuration outage as a missing object.
- Why it matters: a service/configuration failure is silently converted into expected absence, weakening diagnosis and recovery.
- Required correction: classify only object-not-found error codes/shapes as `null`; propagate `NoSuchBucket` and other 404 services errors as `StorageError`. Add contract coverage for a missing object and a nonexistent bucket for both `get` and `head`.
- Owner: builder
- Verification: the new contract tests show missing key → `null`, missing bucket → `StorageError`, and existing object behavior remains green.
- Disposition (P2 only): before merge
- Status: open
