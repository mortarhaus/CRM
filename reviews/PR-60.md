### Code review notes (no blocking finding)
- **Input:** `z.enum(DATE_FORMATS).optional()`. The form maps an empty choice to `undefined`, which leaves the value as it is (the same rule as the timezone and currencies). A value outside the list is refused with `INVALID_INPUT` on `dateFormat`, and nothing is written (the `actions.test.ts` table case `mm/dd/yyyy`).
- **Write path:** `generalPatch` spreads the parsed fields, so `dateFormat` reaches `updateSettings` (version check, row lock, audited). The `crm_app` UPDATE grant on `date_format` has existed since 0025. The save test reads `date_format = "yyyy-mm-dd"` back.
- **Echo:** `GENERAL_CHOICES` now includes `dateFormat`, so a refused no-JS post echoes it. It isn't personal data. The address, registration number, TIN and BRN are still never echoed.
- **"New documents only":** `dateFormat` isn't in `NEW_DOCUMENTS_ONLY`, so a change doesn't count, and the test asserts `newDocumentsOnly: false`. Acceptable: nothing renders a date with it yet, and Phase 4 decides whether issued documents freeze their format.
- **Existing workspaces:** values stored before Q10 (`dd/mm/yyyy`) and null ("Not set") both display correctly. If a value outside the list were ever stored (the DB CHECK allows any text up to 100 characters), the browser would preselect the first option, and the next save would quietly change the format. No code path writes such a value today. Timezone has the same pattern already, so I'm noting it, not filing it.
- **Core test:** every country default is in `DATE_FORMATS`, with no duplicates. Core stays data-only (UNI-04).
- **Role:** the same `action()` and `minRole: "admin"`. The Staff and `NOT_ONBOARDED` refusals are unchanged and still tested.
