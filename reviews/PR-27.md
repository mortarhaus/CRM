### [P2] Runbook gives the wrong invalid-origin failure path for the new image
- Category: documentation / guardrail mismatch
- Rule: UNI-16
- Evidence: `docs/runbooks/phase-0-auth-database.md:198-202` says an invalid production `APP_URL` lets the process start and fails only on the first `/api/auth/*` request. The new `docker/entrypoint.sh:5-7,9-11` runs `dist/migrate.mjs` before either the web or worker process; `apps/web/migrate.ts:5-7` calls `getEnv()` first; `apps/web/src/lib/env.ts:17-20,28-34` rejects a non-HTTPS, non-loopback production `APP_URL` there. The runbook's earlier required-environment paragraph also says validation is not at process start (`:21-23`).
- Failure scenario: An operator gives the image an invalid production origin and waits for a first-request 500, while the container has already exited during its migration preflight and never starts the web server.
- Why it matters: The new image fails safely, but its documented startup and recovery path is wrong. This is limited to the runbook, so P2 is proportionate rather than the default P1 for a guardrail miss.
- Required correction: Distinguish direct `pnpm dev` first-request validation from image startup validation. State that `web` and `worker` validate the environment in the migration entrypoint and exit before listening when production `APP_URL` is invalid; align the failure-recovery instructions with that behavior.
- Owner: builder
- Verification: Run the image with a non-loopback HTTP `APP_URL` and confirm `docker compose up --wait web` fails before health; the runbook predicts that outcome without implying a first auth request is needed.
