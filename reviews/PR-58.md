### Findings

### [P1] The `apk upgrade` floats, and UNI-14 is missing from the self-check
- Category: guardrail mismatch
- Rule: UNI-14 ("Build tooling and integrations pinned; no floating `latest` in CI or deploy"); PROJECT.md §9 ("every dependency is an exact version"); roles/reviewer.md §3 (applicable rule missing from the self-check → P1)
- Evidence: `docker/Dockerfile` runtime stage, `RUN apk upgrade --no-cache musl musl-utils zlib`, with no versions. The self-check lists UNI-06, UNI-16 and UNI-13 only. The PR body (Deviation 1) and DECISIONS ("a build today and a build next month can differ") state the float openly. I checked with a throwaway container from the pinned base (`crm-review-58-apk`, `apk policy`): Alpine 3.24.2, and the v3.24 `main` repo offers exactly one candidate per package, `musl` / `musl-utils` 1.2.6-r3 and `zlib` 1.4-r0.
- Failure scenario: a later Alpine 3.24 update to any of the three packages changes the shipped image with no commit, no review and no DECISIONS line. The same Dockerfile then builds different images for SaaS and self-host on different days.
- Why it matters: the base is pinned by digest precisely so the image is reproducible, and this line undoes that for three system libraries.
- Required correction: pin exactly, `apk add --no-cache musl=1.2.6-r3 musl-utils=1.2.6-r3 zlib=1.4-r0` (or `apk upgrade` with the same `=version` pins). Record the trade-off in DECISIONS: Alpine keeps only the newest build per branch, so when Alpine moves on, the image build fails with a clear "unable to select packages" error until someone re-pins or re-pins the base. That loud failure is the intended behaviour. Add a UNI-14 row to the self-check. If Charlie would rather accept the float, he records it as an exception in DECISIONS in his own words, and the row says so.
- Owner: builder (or Charlie, for the exception)
- Verification: the Dockerfile line at the new head, the DECISIONS text, the UNI-14 row, and a green "Image, Trivy, E2E" run on that head.
