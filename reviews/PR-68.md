### Findings

### [P2] The per-user step-up limit is much looser than the sign-in account cap, and nothing locks a stolen session out
- Category: material risk (a business number that is the builder's own)
- Rule: UNI-02 (rate-limit numbers are owner-approved; spec "Rate limits → Numbers", revision 7); AUTH-06, AUTH-09; plan PR 5 "Bob looks first at: step-up bypass (… missing rate limit)"; roles/builder.md §8
- Evidence: `STEP_UP_VERIFY_USER_LIMIT = TWO_FACTOR_VERIFY_IP_LIMIT` = **10 per 60 s per user** (`limits.ts`), a builder proposal (DECISIONS 2026-11-20 "Decided by: builder"). Every check is counted, success or not, and the window resets every minute. The session branch of Better Auth's `verify-totp` has no lockout (the builder's spike, which I accept). Better Auth accepts a code for 3 steps, so a guess hits with probability about 3 in 10^6. The sign-in password path, by contrast, is capped at **5 failures per 15 minutes per account** (`SIGN_IN_ACCOUNT_FAILURE_LIMIT`).
- Why it matters: step-up exists for the case where someone holds a live session (a stolen cookie, an unattended laptop) but not the phone. At 10 per minute that person can try 14,400 codes a day, about a 4% chance a day and a better-than-even chance over a month, with no alert and no lockout. The sign-in path is far stricter for the same second factor.
- Answer to the builder's question 1 ("are the one-use marker and the per-user limit enough?"): the order of checks is right and the marker is sound (below). The per-user number is not enough as set.
- Required correction: Charlie chooses the number. Bob recommends mirroring the sign-in account cap: count **failures only**, 5 per 15 minutes per user (`consumeUnit`, then `giveBackUnit` with the returned `windowStart` once the code is accepted, as the sign-in counter does), keeping Better Auth's per-IP row and the one-use marker. A user who mistypes five times waits 15 minutes. Update `limits.ts`, the runbook row and DECISIONS, and keep the "11th check" test in line with the new number.
- Owner: Charlie (number); builder (change)
- Disposition (P2 only): **deferred to PR 5b, before `verifyStepUp` becomes reachable**. Nothing calls it yet (no server action exports it, DECISIONS and PR body say so), so the live exposure today is nil. PR 5b (Tasks 14–15) is its first caller and must not merge with the number unchanged unless Charlie has confirmed 10 per 60 s in his own words.
- Status: open

### Code review notes (no further finding)
- **`checkCode` order (builder's question 1): correct.** (1) no 2FA → `TWO_FACTOR_REQUIRED` before anything is spent; (2) the per-user unit; (3) the post to Better Auth, so its per-IP row, origin check and TOTP verify run; (4) the one-use marker, taken only after a valid code. Because the marker comes last, a wrong code never burns a marker. `consume` is one atomic upsert (`where ended or count < max`), so two requests with the same code cannot both take the marker. I also ran a rough two-session concurrent probe (scratch test, deleted): at most one `step_up` row. That probe shares header state between the two calls, so the atomic statement is the real guarantee.
- **Marker design:** the key is an HMAC of the code under an HKDF subkey of `AUTH_SECRET` (`crm step-up code v1`), per user, 120 s. The test asserts no key contains the code. This repeats the pattern of `request-handler.ts`'s account key with a different `info`; acceptable, a shared helper would be tidier but isn't required.
- **Replay and cross-session (the plan's "Bob looks first"):** one code can step up one session of the user once, then not again for 120 s in any session or workspace (test "refuses one code twice"). The sign-in code isn't marked, which DECISIONS discloses; the same user's session is still needed.
- **`beforeTransaction` (question 2):** runs after role and Zod, before idempotency and outside the transaction; a refusal returns without opening one; tests assert the order and that no handler runs. `ActionContext` gets `sessionId`, and `ctx` is built from named fields, so `twoFactorEnabled` doesn't leak into handlers.
- **`require_2fa` (question 2):** checked in `requireWorkspaceMember` after the role check, for Admin and Owner only (spec line 744), and only read when the user has no 2FA, so Staff and 2FA users pay nothing. Every `action()` re-checks it, so a direct POST is refused (AUTH-02). `/settings/security` doesn't call `requireWorkspaceMember`, so the redirect can't loop. Nothing sets the flag yet, so this is inert until a settings PR adds the toggle; its owner question (who may turn it on, and whether that needs step-up) is correctly left open. Two small consequences, both disclosed or unreachable today: the logo route answers 404, and `onboarding/page.tsx` would treat `TWO_FACTOR_REQUIRED` as "nothing to do" if the flag were ever set before onboarding.
- **Migrations (question 3):** 0028 adds the table (PK `(workspace_id, session_id)`, FK to `organization` restrict, as `domain_event` and `notification`). 0029 matches the 0020 template line for line: ENABLE + FORCE, RESTRICTIVE `FOR ALL TO crm_app, crm_purge` with USING and WITH CHECK on `nullif(current_setting('app.workspace_id', true), '')`, per-command PERMISSIVE policies for `crm_app`, `GRANT SELECT, INSERT` and `UPDATE (verified_at)`, no DELETE. `ON CONFLICT DO UPDATE` needs SELECT, INSERT and UPDATE on that column, all granted. The `privileges.ts` entry and the isolation fixture agree; the manifest test passes.
- **`requireStepUp`:** the age is compared on the database clock against `verified_at` written by `now()` of the step-up transaction, so skew can only make the window slightly shorter. A row is bound to workspace and session; another session of the user and another workspace are refused (tested).
- **Spike:** I accept the builder's reading of Better Auth 1.7.14: for an enrolled user the session branch issues, rotates and ends nothing, and the test "issues, rotates and ends no session" proves it against the real handler (session count, no Set-Cookie, same session id). A user whose `twoFactorEnabled` is false is refused before the post, which keeps the enrolment branch (which does rotate sessions) out of reach.
- **Failed attempts aren't audited.** The spec's `auth_audit_log` list covers logins and 2FA changes, not failed step-up, so this isn't a gap against the spec; the P2 above is the practical control.
- **Scope:** the `EMAIL_FROM` docs and one env test line ride along (ASK 7 said "in PR 5"); no product code. Size is over target because of tests (394 of 663); product code is 215.
