### [P2-1] One auth request holds a pool connection, and a per-user lock, for its whole run
- Category: material risk (availability; a forward hazard for Task 22)
- Rule: spec "Authentication and sessions" (Phase 1 rate limits), UNI-04; plan Task 22 (rate-limit storage)
- Evidence:
  - Each auth POST now holds one of the 10 pool connections (`createDb` `max: 10`) from the first query to commit, including the password hash and any lock wait. Requests for one email wait on that user's row lock for up to 5 s, each one holding a connection while it waits.
  - My probe (`createAuth` as configured, 30 parallel wrong-password sign-ins): an unrelated `select 1` on the same pool took **161 ms** when all 30 used one email, against **15 ms** when they used 30 different emails. All 30 answered 401.
  - Forward hazard: a query in the request that does not go through the routed db needs a second connection. With the pool full of open request transactions, that waits with no timeout, which is a pool deadlock. This is why `/organization/*` is left outside the transaction.
